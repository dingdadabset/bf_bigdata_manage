# StarRocks 角色模板化治理需求梳理

生成日期：2026-06-04

## 1. 背景

当前 StarRocks 授权已经具备以下基础能力：

- 可查询用户列表。
- 可查询用户当前 live 权限。
- 可创建用户。
- 可创建角色并向角色挂载库表权限。
- 可将角色绑定到用户。

但目前仍缺少一套面向治理的标准流程，来回答下面几个问题：

1. 角色是不是应该和模板绑定。
2. 制定模板前是否必须先知道用户当前有哪些权限。
3. 是否还需要知道用户实际使用了哪些权限。
4. 历史遗留的直授权应该如何收敛进角色体系。

本文档用于把 StarRocks 权限治理从“能授权”推进到“能标准化治理”。

## 2. 核心结论

### 2.1 角色与模板的关系

- `权限模板`：标准权限包定义，是治理规则层。
- `角色`：模板在某个集群、业务域、库表范围内的落地载体，是执行层。
- `用户绑定`：用户优先绑定角色，尽量不直接散落授权。

结论：

- 角色应当和模板绑定。
- 模板不应直接等同于单个角色编码，而应当是角色的上层标准定义。
- 一个模板可在不同库域、不同环境下派生多个角色。

示例：

- 模板：`只读分析模板`
- 派生角色：`sr_ods_readonly`
- 派生角色：`sr_ads_order_readonly`

### 2.2 制定模板前是否要知道用户权限

必须知道。

原因如下：

1. 不知道当前权限，就无法判断历史授权模式。
2. 不知道当前权限，就无法归纳常见权限组合。
3. 不知道当前权限，就无法评估新模板会覆盖多少存量用户。

因此，模板设计前必须先形成：

- `用户 -> 当前 live 权限` 清单

### 2.3 是否要知道用户“实际使用的权限”

建议知道，但不作为 V1 的硬前置。

原因如下：

- 仅根据当前权限做模板，容易把历史临时授权、冗余授权一起固化进模板。
- 如果能知道用户实际访问过哪些库表、执行过哪些操作，可以更准确地裁剪模板。

因此建议分层处理：

- `V1`：先基于当前 live 权限梳理模板候选。
- `V2`：再引入查询审计、访问日志、作业来源等“实际使用证据”做模板瘦身和治理。

## 3. 目标

建设一套适用于 StarRocks 的角色模板化治理流程，达到以下目标：

1. 能盘点指定 StarRocks 集群中的用户及其当前权限。
2. 能识别高频重复的权限组合，形成模板候选。
3. 能将模板实例化为 DGA 中的 StarRocks 角色。
4. 能把用户批量绑定到目标角色。
5. 能识别“角色外例外权限”和“疑似冗余权限”。
6. 为后续直授权收敛、历史权限接管、风险治理提供基础数据。

## 4. 范围

### 4.1 V1 范围

V1 聚焦“先梳理、再标准化、再绑定”：

1. 用户盘点
2. 当前权限盘点
3. 模板候选生成
4. 角色建立与维护
5. 用户批量绑定角色
6. 差异清单输出

### 4.2 V2 范围

V2 聚焦“用真实使用情况优化模板”：

1. 引入查询日志或审计日志
2. 形成用户实际使用权限画像
3. 对模板进行裁剪和风险分级
4. 推动直授权收敛

### 4.3 暂不纳入本次范围

1. 自动回收所有历史直授权
2. 全自动把历史权限直接归并进 StarRocks 角色
3. 完全无人工确认的模板自动生成和自动下发

## 5. 概念模型

建议引入以下治理概念：

### 5.1 权限模板

字段建议：

- `templateCode`
- `templateName`
- `cluster`
- `scopeType`
- `resourceDomain`
- `permissionItems`
- `riskLevel`
- `status`
- `description`

说明：

- 模板代表标准权限组合，不直接对应某个具体用户。

### 5.2 角色

字段沿用现有 RBAC 角色模型，补充模板关联关系：

- `roleCode`
- `roleName`
- `cluster`
- `authBackend`
- `engineType`
- `templateCode`
- `owner`
- `status`

说明：

- 一个角色应尽量来源于某个模板。
- 没有模板来源的角色视为“非标准角色”。

### 5.3 用户权限画像

建议分两类：

1. `当前权限画像`
   - 来自 live 权限查询。
2. `实际使用画像`
   - 来自查询日志、审计日志、作业访问证据。

### 5.4 例外权限

对于未被角色覆盖、但业务上必须保留的权限，需要单独标记为：

- `DIRECT_EXCEPTION`
- `TEMP_EXCEPTION`
- `UNMANAGED_HISTORICAL`

## 6. 输入数据

模板制定和角色绑定至少需要以下输入：

### 6.1 必需输入

1. StarRocks 用户列表
2. 用户当前 live 权限明细
3. 库、表、权限类型基础元数据

### 6.2 强烈建议输入

1. 用户近 30/60/90 天实际访问记录
2. SQL 审计日志
3. 作业归属或系统账号用途说明
4. 业务负责人或数据域负责人信息

### 6.3 可选输入

1. 组织架构或项目组映射
2. 用户所属业务线
3. 历史工单记录
4. 风险标签和敏感库标签

## 7. 业务流程

### 7.1 流程一：当前权限盘点

目标：

- 看清楚“现在每个用户实际被授予了什么”。

流程：

1. 选择 StarRocks 集群。
2. 导入或同步 StarRocks 用户到 DGA。
3. 对每个用户拉取当前 live 权限。
4. 形成 `用户-库/表-权限` 清单。
5. 输出按用户、按库域、按权限组合的统计报表。

输出：

- 用户权限明细表
- 权限组合聚类结果
- 异常权限初筛结果

### 7.2 流程二：模板候选生成

目标：

- 从用户现有权限组合中总结出标准模板。

流程：

1. 将权限按数据库、表、权限类型归一化。
2. 对用户权限组合进行聚类。
3. 标记高频组合为模板候选。
4. 对低频且高风险组合标记为例外候选。
5. 由管理员确认模板名称、适用范围、风险级别。

输出：

- 模板候选列表
- 每个模板的覆盖用户数
- 模板外权限清单

### 7.3 流程三：模板落地为角色

目标：

- 将标准模板沉淀为可执行的 RBAC 角色。

流程：

1. 选中模板候选。
2. 生成或维护角色编码。
3. 将模板中的权限项挂到角色上。
4. 标记角色与模板关系。
5. 生成角色说明和适用范围。

输出：

- 标准角色目录
- 角色权限范围
- 模板与角色映射关系

### 7.4 流程四：用户绑定角色

目标：

- 让用户从“散落权限”逐步转向“角色绑定”。

流程：

1. 选中角色。
2. 选中目标用户列表。
3. 执行 dry-run，预览将新增的绑定关系。
4. 确认后批量绑定角色。
5. 输出成功、失败、已绑定、用户不存在等结果。

输出：

- 批量绑定结果
- 用户与角色关系清单

### 7.5 流程五：差异治理

目标：

- 识别标准角色体系之外的权限残留。

差异类型：

1. `已绑角色但 live 权限少于角色范围`
2. `已绑角色但 live 权限多于角色范围`
3. `用户仅有直授权，未进入角色体系`
4. `角色存在但无用户使用`
5. `模板存在但未落地角色`

输出：

- 差异清单
- 收敛建议
- 风险优先级

## 8. 页面需求

建议新增或增强以下页面能力。

### 8.1 StarRocks 权限盘点页

目标：

- 快速展示 StarRocks 用户和当前权限分布。

页面能力：

1. 选择集群
2. 同步用户
3. 批量拉取权限
4. 按用户查看 live 权限
5. 按库/表统计授权分布
6. 导出盘点结果

### 8.2 模板治理页

目标：

- 管理模板候选和标准模板。

页面能力：

1. 查看模板候选
2. 查看模板覆盖用户数
3. 确认模板为正式模板
4. 标记风险级别
5. 查看模板与角色映射关系

### 8.3 角色治理页增强

目标：

- 让角色不再只是孤立维护，而是有模板来源。

页面能力：

1. 创建角色时可关联模板
2. 显示角色来源模板
3. 显示角色覆盖用户数
4. 显示角色外例外权限数量
5. 支持批量绑定用户

### 8.4 差异治理页

目标：

- 专门用于收敛历史遗留授权。

页面能力：

1. 已绑角色但权限不一致用户列表
2. 仅有直授权用户列表
3. 模板外权限清单
4. 建议动作
5. 工单或审批备注

## 9. API 需求

### 9.1 复用现有接口

现有可直接利用的接口：

1. `POST /api/access/import-auth-backend`
   - 导入 StarRocks 用户
2. `GET /api/access/resources/principals`
   - 查询用户列表
3. `GET /api/access/resources/permissions`
   - 查询用户当前 live 权限
4. `POST /api/access/roles`
   - 创建角色
5. `POST /api/access/roles/{roleCode}/permissions`
   - 给角色挂权限
6. `POST /api/access/roles/{roleCode}/assignments/batch/dry-run`
   - 批量绑定预演
7. `POST /api/access/roles/{roleCode}/assignments/batch`
   - 批量绑定执行

### 9.2 建议新增接口

#### A. 权限盘点

1. `POST /api/access/starrocks/inventory/permissions`
   - 批量扫描用户当前 live 权限
2. `GET /api/access/starrocks/inventory/users`
   - 查询盘点后的用户权限汇总
3. `GET /api/access/starrocks/inventory/users/{username}`
   - 查询指定用户权限画像

#### B. 模板候选

1. `POST /api/access/templates/candidates/generate`
   - 基于盘点结果生成模板候选
2. `GET /api/access/templates/candidates`
   - 查询模板候选
3. `POST /api/access/templates`
   - 确认模板候选为正式模板

#### C. 模板与角色映射

1. `POST /api/access/templates/{templateCode}/roles`
   - 从模板创建角色
2. `PUT /api/access/roles/{roleCode}/template`
   - 角色关联模板
3. `GET /api/access/templates/{templateCode}/roles`
   - 查询模板下角色

#### D. 差异治理

1. `GET /api/access/starrocks/reconciliation`
   - 查询角色、模板、用户之间的差异
2. `POST /api/access/starrocks/reconciliation/actions`
   - 对差异项提交治理动作

### 9.3 V2 建议新增接口

1. `GET /api/access/starrocks/usage/users/{username}`
   - 查询用户实际访问画像
2. `GET /api/access/starrocks/usage/templates/{templateCode}`
   - 查询模板对应的实际使用情况

## 10. 数据模型建议

建议新增模板主表和模板权限表。

### 10.1 模板主表

表名建议：

- `auth_permission_template`

核心字段：

- `id`
- `template_code`
- `template_name`
- `cluster`
- `engine_type`
- `auth_backend`
- `resource_domain`
- `risk_level`
- `status`
- `description`
- `created_by`
- `updated_by`
- `create_time`
- `update_time`

### 10.2 模板权限表

表名建议：

- `auth_permission_template_item`

核心字段：

- `id`
- `template_code`
- `resource_type`
- `database_name`
- `table_name`
- `permission`
- `status`

### 10.3 角色模板映射

可选两种方式：

1. 在 `auth_role` 上直接增加 `template_code`
2. 单独维护 `auth_role_template_mapping`

建议 V1 采用方式 1，结构更简单。

## 11. StarRocks 特有差异点

### 11.1 只支持 USER，不支持 LDAP 组治理模型

影响：

- StarRocks 模板治理应以用户为中心，而不是以组为中心。

### 11.2 当前可做 live 权限盘点，但不支持历史权限接管流程

影响：

- 目前不能像 Hive + Sentry 那样直接把历史 live 权限一键接管为 DGA 历史接管记录。
- StarRocks 更适合先做“盘点 -> 模板 -> 角色 -> 绑定 -> 差异治理”。

### 11.3 当前没有原生角色盘点接管流程

影响：

- StarRocks 后端已有角色暂时不能直接被 DGA 自动盘点并接管为本地角色目录。
- V1 推荐以 DGA 本地角色为主进行标准化治理。

### 11.4 实际使用证据可能需要额外接日志

影响：

- 如果要判断“某权限是否真的在用”，需要额外引入 StarRocks 查询日志、审计日志或作业访问证据。

## 12. V1 落地建议

建议按下面顺序推进：

### 第一步：先做盘点

产出：

- 用户清单
- 当前 live 权限清单
- 权限组合聚类结果

### 第二步：做模板候选

产出：

- 高频模板候选
- 低频例外权限候选

### 第三步：模板落地角色

产出：

- 标准角色目录
- 角色模板映射

### 第四步：批量绑定

产出：

- 用户角色绑定结果

### 第五步：做差异治理

产出：

- 角色外权限清单
- 非标准用户清单
- 后续收敛计划

## 13. 验收标准

### 13.1 V1 验收

1. 能选中 StarRocks 集群完成用户导入。
2. 能查询任意用户当前 live 权限。
3. 能生成模板候选，并展示候选覆盖人数。
4. 能将模板落地为角色。
5. 能执行批量角色绑定，并看到 dry-run 与执行结果。
6. 能输出模板外权限与差异清单。

### 13.2 V2 验收

1. 能看到用户最近使用过的库表权限。
2. 能区分“当前有权限但长期未使用”和“当前高频使用”的资源。
3. 能基于使用证据优化模板范围。

## 14. 风险与注意事项

1. 如果只基于当前 live 权限建模板，容易把历史冗余权限固化下来。
2. 如果没有业务 owner 参与，模板命名和适用范围容易失真。
3. 如果缺少差异治理页，用户绑定角色后仍可能保留大量角色外直授权。
4. StarRocks 现阶段更适合渐进式治理，不建议一步到位做自动回收。

## 15. 推荐实施策略

建议采用两阶段实施。

### 阶段 A：先把标准体系立起来

目标：

- 有盘点
- 有模板
- 有角色
- 能批量绑定

### 阶段 B：再做治理收敛

目标：

- 有实际使用证据
- 能发现冗余权限
- 能推动历史直授权逐步退出

## 16. 本次建议结论

对当前 StarRocks 场景，最合理的方向不是“先拍脑袋建角色”，而是：

1. 先盘点用户当前权限
2. 再形成模板候选
3. 然后把模板落地成角色
4. 再批量绑定用户
5. 最后治理角色外权限

如果后续确认要进一步做“历史权限自动收敛”，建议单独立项为：

- `StarRocks 历史权限接管与差异治理增强`
