# 数据治理平台（DGA）项目立项报告

---

## 一、项目背景：现状与解决的问题

### 现状

公司同时运行 CDH、HDP 等多套大数据平台，数据引擎涵盖 Hive、StarRocks、ClickHouse 等。当前各平台的元数据、权限、质量治理分散在多个独立工具中，缺乏统一管理入口。

### 要解决的问题

| 问题 | 具体表现 |
|------|---------|
| **权限管理分散** | LDAP 用户管理、Ranger/Sentry 授权分散，人工操作效率低且易出错；状态不一致时回收失败，缺乏强制兜底手段。 |
| **元数据不统一** | 多套 Hive Metastore 和引擎各自独立，分析师找表难，口径不统一。 |
| **质量不可控** | 缺少全链路质量监控，坏数据无法及时发现和阻断。 |
| **合规风险** | 授权审计覆盖不足，无法满足数据安全法和内审要求。 |
| **无治理闭环** | 从申请→审批→授权→回收→审计的完整链路尚未打通。 |

---

## 二、项目思路与方案

### 总体思路

构建一站式数据治理平台（DGA），以**统一元数据 + RBAC 授权中心 + 质量监控 + 审计运营**为核心能力，分期建设，逐步替代人工数据治理操作。

### 一期方案（当前实施中）

**核心架构**

```
前端 Vue 2 + Vite  ←→  后端 Spring Boot 2.7  ←→  MySQL / LDAP / Ranger / Sentry
```

**一期交付的四大模块：**

| 模块 | 功能 | 当前进度 |
|------|------|---------|
| **授权中心** | RBAC 角色管理、角色绑定、权限子集下发/回收、权限校验、批量绑定 | 已开发完成，持续优化 |
| **安全集成** | LDAP 用户/组识别、Ranger/Sentry 多后端适配、管理员强制回收 | 已完成 |
| **数据地图** | 多数据源元数据采集、资产目录、搜索 | 开发中 |
| **开放 API** | 对外授权接口，支持第三方系统集成 | 已发布 |

**关键技术设计：**

- **RBAC 权限模型**：角色定义权限范围，主体绑定角色后获得权限子集
- **多后端适配器**：统一 `AuthorizationProvider` 接口，隔离 Sentry/Ranger/Doris/StarRocks 差异
- **权限校验机制**：Live vs Recorded 双重比对，实时反馈授权一致性
- **强制回收（管理员专用）**：绕过角色链路，按用户逐条精确回收，解决后端角色不同步问题

### 二至四期规划

| 阶段 | 核心能力 |
|------|---------|
| 二期（规范期） | 数据质量中心：规则管理、监控任务、告警熔断 |
| 三期（优化期） | 成本治理：冷热数据识别、僵尸表清理、存储分析 |
| 四期（智能期） | AI 治理：LLM 自动打标、SQL 诊断、血缘自动解析 |

## 四、项目难点与风险

### 1. 多后端状态不一致风险（当前最突出）

**问题**：同样的授权操作在 DGA 本地记录和 Ranger/Sentry 后端之间可能不一致，回收时容易因为后端角色不存在而中断。

**应对措施**：
- 已实现异常的简短可读处理
- 已增加管理员专用"强制按用户精确回收"兜底按钮
- 计划后续增加状态巡检和自动修复任务

### 2. 多集群多后端适配复杂度

**问题**：CDH（Sentry/Hive SQL）、HDP（Ranger REST API）、StarRocks、Doris 授权方式不同，异常返回格式各异。

**应对措施**：
- 统一 `AuthorizationProvider` 接口，隔离实现差异
- 已适配 Sentry（JDBC）、Ranger（REST）、Doris/StarRocks（SQL）三种模式

### 3. LDAP 连接稳定性

**问题**：LDAP 连接超时或不可用会影响用户查找和授权执行。

**应对措施**：
- 熔断处理，LDAP 失败不影响已缓存用户操作
- 备用连接配置

### 4. 用户接受度与推广

**问题**：新平台推广初期，用户习惯用老方式操作。

**应对措施**：
- 分阶段推广，先试点后铺开
- 保持与现有操作流程兼容
- 提供开放 API，降低集成成本

### 5. 数据质量建设周期长

**问题**：质量规则建设需要大量业务理解，非纯技术工作。

**应对措施**：
- 一期先打基础（元数据 + 权限），二期再攻坚质量
- 优先覆盖核心业务域
